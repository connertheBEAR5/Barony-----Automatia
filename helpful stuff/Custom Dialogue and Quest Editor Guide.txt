BARONY AUTOMATIA CUSTOM DIALOGUE + QUEST EDITOR GUIDE
=====================================================

This is the maintained guide for the remastered Zed dialogue and quest editor.
It describes the current visual editor and runtime contract. Historical button
roadmaps have been removed so new authors do not have to reconstruct the UI's
implementation history.


1. THE TWO IDENTITIES
=====================

Dialogue resources live at:

    dialogue/<dialogue_file_id>.json

An NPC's Custom Dialogue ID selects that filename without the .json suffix.

    NPC Custom Dialogue ID: village_guard
    Resource:               dialogue/village_guard.json

Dialogue/File ID and Quest ID are separate:

    Dialogue/File ID
        Selects the resource. Renaming the file changes this identity.

    Quest ID (root quest_id)
        Selects persistent quest progress, journal state, conditions,
        objectives, completion, failure, and quest variables.

    Example
        Dialogue/File ID: village_guard
        Quest ID:         convince_the_guard

Renaming village_guard.json does not rename convince_the_guard. The editor
keeps this separation visible and relinks quest references only when the author
directly edits quest_id.

Dialogue schema version 1 also retains the original one-line form:

    {"version": 1, "text": "Hello, traveler."}

Conversation presents this as a Legacy One-Line Dialogue with an editable NPC
text field. CONVERT TO EDITABLE NODE GRAPH preserves the line as node 0 and
unlocks responses, conditions, actions, and graph preview. Undo restores the
legacy form until the document is saved.


2. OPENING AND LAYOUT
=====================

Open an NPC's sprite properties and use the custom-dialogue EDIT control. The
remastered window uses stable application-style regions drawn with Zed/Barony's
existing panels, fonts, buttons, colors, and input system:

    Top navigation
        Files | Conversation | Quest | Tutorials | JSON | Preview | Validation

    Left file rail
        Searchable dialogue resources, quest metadata, saved/unsaved state,
        and validation badges.

    Main workspace
        The active page: conversation flow, quest builder, tutorial recipe,
        JSON, preview, or diagnostics.

    Inspector
        Semantic controls for the selected node, response, condition, action,
        objective, giver, or item.

    Status area
        Current file, dirty state, validation counts, and contextual messages.

Long labels are clipped or wrapped inside their panels. Lists have independent
scrolling where applicable. No separate web browser or GUI framework is used.


3. FILE HOME AND NEW DIALOGUE WIZARD
====================================

The file rail searches filename/Dialogue ID, Quest ID, and quest title. Each
entry reports OK, warning count, or error count.

File actions:

    New
        Opens the four-step wizard.

    Rename
        Changes the dialogue filename only. It refuses blank IDs, unsafe IDs,
        and collisions. It does not silently rename quest_id.

    Duplicate
        Loads the source through the shared document model and atomically saves
        an independent copy with a unique filename.

    Delete
        Requires confirmation and never targets a directory or wildcard.

    Reload
        Reloads the selected file after the dirty-state prompt.

    Save
        Validates and atomically replaces the selected file. The old file is
        not truncated before the replacement is ready.

New Dialogue wizard:

    Step 1 - Identity
        Dialogue/File ID and a live dialogue/<id>.json preview.

    Step 2 - Conversation
        First NPC line, first response, and a starter template.

    Step 3 - Quest
        Optional quest, Quest ID, title, summary, repeatable state, and giver
        source (none, cursor tile, or selected persistent NPC).

    Step 4 - Finish
        Collision check, validation result, and atomic Create & Open.

Starter templates:

    Empty Conversation
    Greeting / One Choice
    Two-Choice Branch
    Quest Giver
    Recruitable NPC

The wizard refuses an existing filename and never overwrites a resource.


4. MAKE AN NPC SAY HELLO
=======================

    1. Choose New.
    2. Enter a Dialogue/File ID.
    3. Choose Greeting / One Choice.
    4. Enter the NPC line and player response.
    5. Create & Open.
    6. Validate, Preview, then Save.
    7. Put the Dialogue/File ID on the NPC sprite.

A minimal resource is:

{
  "version": 1,
  "start_node": 0,
  "nodes": [
    {
      "id": 0,
      "text": "Hello, traveler.",
      "next": 0,
      "choices": [
        {"id": "hello", "text": "Hello.", "next": 0}
      ]
    }
  ]
}


5. CONVERSATION WORKSPACE
=========================

The Conversation page presents nodes as readable flow cards. A node shows its
numeric ID, START marker, NPC text, automatic destination, redirect summary,
one-time node-action summary, and response destinations.

Node operations:

    Add, duplicate, select, edit, and delete
    Set as start node
    Edit numeric ID and NPC text
    Select automatic next destination directly
    Add/remove a redirect condition
    Add/remove a one-time node action

Safe deletion blocks removal when the node is:

    the start node,
    the last node,
    another node's next destination,
    a response destination,
    a redirect true/false destination, or
    referenced by node_seen.

Duplicating a node creates fresh node/choice/action IDs and repairs copied
self-links to point at the duplicate.

Response operations:

    Add, duplicate, select, edit, delete, move up, and move down
    Edit globally unique stable response ID
    Edit response text
    Choose destination directly
    Toggle once-only behavior
    Add one condition or an AND list of conditions
    Stack multiple independent action fields

Adding or editing one action does not erase unrelated action fields.


6. CONDITION BUILDER
====================

Select a response and use Add Condition. A response may use singular
"condition" or a "conditions" array. Every entry in the array must pass
(logical AND). The visual builder preserves either valid representation.

Choice condition families:

    has_item
        Vanilla item or S.A.M. stable_id plus positive count.

    has_gold
        Non-negative gold amount.

    quest_started
    quest_accepted
    quest_completed
    quest_failed
        Referenced quest ID.

    quest_stage
        Quest ID, integer stage, and comparison.

    objective_completed
    objective_incomplete
        Quest ID and objective ID.

    world_flag
    npc_flag
        Normalized ID and required Boolean value.

    world_variable
    npc_variable
        Normalized ID, integer value, and comparison.

Comparisons:

    equals
    not_equals
    at_least
    at_most

There is no quest_variable condition in the current runtime. Quest variables
can be changed by actions but are not an authorable condition family.

Node redirect conditions use:

    has_item, has_gold,
    quest_started, quest_accepted, quest_completed, quest_failed, quest_stage,
    node_seen,
    world_flag, npc_flag, world_variable, npc_variable

A node redirect additionally requires direct true_node and false_node
destinations. has_item and has_gold redirects may optionally consume the item
or gold. Node quest_stage supports equals, at_least, and at_most; the current
runtime does not accept not_equals for node redirects.


7. ACTION BUILDER
=================

Select a response and choose Add Action, then an intent-based category. Each
action has plainly named controls. Multiple fields coexist in one action
object.

Choice action fields:

    Quest
        quest_start       Start the current root quest.
        quest_accept      Accept the current root quest.
        quest_stage       Set its integer stage.
        quest_complete    Complete it.
        quest_fail        Fail it.
        quest_reset       Reset it; requires repeatable player scope.

    Rewards and costs
        reward_gold       Give a non-negative amount.
        remove_gold       Take a non-negative amount.
        reward_item       Give an item reference and count.
        remove_item       Take an item reference and count.
        status_effect     Effect ID, seconds, strength, and enabled state.

    Objectives
        objective_complete
        objective_clear

    Mechanisms and NPC
        set_power         Tile X/Y and powered Boolean.
        recruit_npc       Uses the generic follower path.

    Flags
        set_world_flag
        set_npc_flag

    Variables
        set_quest_variable
        add_quest_variable
        set_world_variable
        add_world_variable
        set_npc_variable
        add_npc_variable

One-time node actions support exactly:

    id
    quest_accept
    quest_complete
    quest_stage
    reward_gold
    reward_item
    set_world_flag
    set_world_variable
    add_world_variable
    set_npc_flag
    set_npc_variable

The node action ID is required and globally unique within the document. It is
the persistent once-only key. Choice-only actions are not offered on nodes.


8. ITEMS AND S.A.M. 2.1
=======================

The item picker searches vanilla items and the existing editor tooling catalog
at ~/.barony/sam_item_catalog.json. Vanilla selections store their numeric
ItemType as a string. Legacy aliases remain supported:

    torch / tool_torch
    healing_potion / potion_healing

Do not store a custom runtime numeric item ID. S.A.M. numbers are session-local.
Custom items use a namespaced persistent registry ID:

    "reward_item": {
      "stable_id": "my_mod:crystal",
      "count": 1
    }

Custom catalog selections store stable_id, never the catalog's last runtime
number. The catalog is an editor hint; the live runtime registry remains
authoritative. The runtime resolves stable_id through that existing generic
S.A.M. registry.
It does not create a dialogue-specific registry and does not clamp a custom ID
into the vanilla range. When stable_id is present it is authoritative; if it
cannot be resolved, the runtime never falls back to an unrelated "item" value.

Unavailable stable items remain preserved in JSON and produce validation
warnings. An unavailable item condition is false, an unavailable choice reward
is rejected before costs/state changes, and an unavailable one-time node reward
defers the complete node action without setting its once flag.


9. QUEST BUILDER
================

The Quest page has Overview, Objectives, and Quest Giver sections.

Overview fields:

    root quest_id
    title
    summary
    objective              General journal objective text
    completed_text
    failed_text
    scope
    repeatable

The visual scope selector exposes player, party, and world because those values
are valid stored metadata. The current live dialogue runtime still executes
quest ownership as player scope. Choosing party/world shows a warning and
safely falls back to player behavior; it does not promise shared ownership.

Objectives are ordered and support:

    id                     Unique normalized ID
    text                   Active text
    completed_text
    stage
    optional
    progress_variable
    target                 Positive integer
    defeat_id              Positive authored defeat ID
    map_marker             Map, non-negative X, non-negative Y

Objectives can be added, duplicated, deleted, and reordered. Renaming an
objective relinks current-document conditions and actions. Deletion is blocked
while a response condition/action still references the objective.


10. QUEST GIVER
===============

Static origin:

    "origin": {
      "label": "Village Guard",
      "map": "village.lmp",
      "x": 12,
      "y": 8
    }

Tracked origin:

    "origin": {
      "label": "Village Guard",
      "map": "village.lmp",
      "track_npc": true,
      "npc_persistent_id": 125
    }

Use Cursor Tile captures a valid editor tile. Use Selected NPC requires a
positive persistent ID, normally assigned after saving the map. Clear Giver
removes the origin. The editor never silently creates a marker at 0,0 when no
valid cursor or NPC is available.

A tracked marker appears only while its NPC is available in the relevant map
context and no longer acts as an ordinary giver marker after recruitment.


11. PREVIEW / TEST
==================

Preview runs an in-memory sandbox. It uses the shared condition/action model
and never mutates game state, persistent story data, an NPC, or the file.

Sandbox inputs include gold, items, flags, variables, quest states, seen nodes,
and used response IDs. The preview shows:

    current NPC line,
    visible responses,
    semantic AND-condition summaries,
    response action summaries,
    current simulated gold/items/flags/quest state, and
    actions that require a real game world.

Reset restores the initial sandbox state. Status effects, mechanism power, and
NPC recruitment are reported as unavailable simulation actions and still need
manual game testing. Preview is not proof of network, audio, journal rendering,
or world presentation.


12. JSON AND VALIDATION
=======================

The JSON page always reflects the same in-memory document as Visual Mode.
Advanced editing parses into a temporary document first. Apply replaces the
model only after parsing succeeds; Cancel returns without changing it. A parse
failure never overwrites the last good document or the on-disk file.

The model retains the full RapidJSON DOM. Editing one known field preserves
other valid fields and unknown extension objects/arrays/scalars. Unknown fields
are shown as informational diagnostics and remain accessible in Advanced JSON.

Validation has Error, Warning, and Info severities plus structured file/quest/
node/response/condition/action/objective locations. Selecting a diagnostic
navigates to the relevant editor object when possible.

Examples of errors:

    invalid schema/version or root
    duplicate node, response, objective, or node-action ID
    broken start/next/branch destination
    unreachable node
    missing objective reference
    invalid item/effect/count/comparison/range
    quest action without quest_id
    invalid repeatable reset

Examples of warnings/info:

    normalized identifiers
    unavailable S.A.M. stable item
    party/world scope falling back to player
    preserved unknown extension fields

Documents are capped at 64 KiB to match the current runtime resource limit.

14. MULTIPLAYER, PERSISTENCE, AND SPATIAL CONTEXT
=================================================

Dialogue consequences remain host-authoritative. A remote client sends only
the selected response index and NPC UID. The host checks its pending dialogue,
NPC identity, response bounds, conditions, one-time quest state, reward/item
availability, and costs before applying supported consequences. The host then
syncs existing story state. Clients do not authoritatively grant rewards or
change quests.

The remaster reuses the existing persistent story backend for:

    player quest state, stages, objectives, and quest variables;
    world flags and variables;
    per-player NPC flags, variables, current nodes, seen nodes, and used choices;
    one-time node action flags; and
    companion/character save import and export.

NPC story keys retain the active MapInstance identity. Interaction and follower
systems retain the entity's playableFloor and MapInstance boundaries. The
dialogue remaster does not reinterpret authoredMapLayer or local model Z and
does not add a second spatial/identity system. Upper-floor and multi-instance
gameplay still require the graphical checks below.


15. MINI MIMIC
==============

Mini Mimic disposition, recruitability, Custom Dialogue enabled state,
Dialogue Resource, display name, and Baby/Scaled Mimic appearance remain
independent authored properties. Dialogue takes interaction priority while the
NPC is not yet a follower. recruit_npc uses the shared follower system and does
not erase customDialogueID or create a Mini-Mimic-specific quest/network/save
path. Generic inventory and S.A.M. stable-item seams remain authoritative.


16. TROUBLESHOOTING
===================

File is not listed
    Confirm it is dialogue/<id>.json, valid JSON, and no larger than 64 KiB.

NPC opens the wrong text
    The sprite's Custom Dialogue ID must match the filename, not quest_id.

Response is missing
    Open Preview/Validation and inspect its conditions, once-only used state,
    referenced quest/objective IDs, item count, and gold amount.

Quest action reports an error
    Add a non-empty root quest_id and Quest metadata. quest_reset additionally
    requires repeatable player scope.

Stable custom item is unavailable
    Confirm the namespaced ID exists in the active S.A.M. catalog. Never replace
    it with a session runtime number.

Tracked giver has no marker
    Save the map to assign a positive persistent NPC ID, select the NPC, bind it,
    and confirm the origin map/context.

Advanced JSON will not apply
    Correct the parse error. The previous good document is intentionally kept.


17. GRAPHICAL AND REAL-GAME ACCEPTANCE (NOT AUTOMATED)
======================================================

These remain unchecked until a person observes them in the actual editor/game.

Editor:

    [ ] Window layout at common and low editor resolutions
    [ ] No text, buttons, panels, or hitboxes overlap
    [ ] Mouse selection and editing
    [ ] Keyboard navigation and text entry
    [ ] Controller focus is usable and never trapped
    [ ] Independent scrolling works
    [ ] Filename/Dialogue ID/Quest ID/title search works
    [ ] Wizard and all five starter templates work
    [ ] Rename leaves quest_id unchanged
    [ ] Duplicate creates an independent file
    [ ] Delete confirms and targets the selected file only
    [ ] Dirty prompts cover switch/reload/rename/delete/close
    [ ] Conversation navigation and direct destinations are readable
    [ ] Node/response/condition/action inspectors are understandable
    [ ] Multiple actions survive adding/removing another action
    [ ] Quest, objective, marker, and giver editing work
    [ ] Tutorial Library is readable and searchable
    [ ] Preview resets without persistent side effects
    [ ] JSON Apply/Cancel and parse-error recovery work
    [ ] Validation navigation reaches the intended object

Game:

    [ ] Basic, linear, and branching conversation
    [ ] Once-only response
    [ ] Item/gold conditions and reward/cost transfer
    [ ] Quest accept/stage/complete/fail/reset and journal text
    [ ] Objective complete/clear and map markers
    [ ] Flags and variables
    [ ] Status effect
    [ ] Mechanism power action on the intended playable floor
    [ ] Recruit an ordinary NPC
    [ ] Mini Mimic dialogue plus recruitment with both appearances
    [ ] Upper-floor NPC interaction remains floor-local
    [ ] Sibling MapInstances do not share NPC-local dialogue state
    [ ] Two real clients keep private player quest progress
    [ ] Dedicated server remains authoritative
    [ ] Save, restart, and reconnect restore story/follower state
    [ ] Available and unavailable S.A.M. stable-item cases

Compilation, document tests, and source-contract characterization do not mark
these graphical, real-client, audio, or presentation checks complete.
