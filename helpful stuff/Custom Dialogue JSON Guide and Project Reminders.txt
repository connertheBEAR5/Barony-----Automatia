BARONY AUTOMATIA CUSTOM DIALOGUE JSON GUIDE
AND PROJECT REMINDERS
============================================================

STATUS NOTE (2026-08-29)
------------------------
This is a compact historical quick reference. The maintained authoring guide is
"Custom Dialogue and Quest Editor Guide.txt"; the complete implementation and
remaining-work summary is in "Barony Automatia Complete Features Guide.txt".
Where this quick reference and those guides differ, use the maintained guides
and current source tree.

Current integration note: authored Mini Mimics can enable custom dialogue and
recruitability independently. A dialogue choice may recruit the NPC, and that
uses the generic follower/owner/HUD/network/persistence path. Per-player story
state and NPC dialogue configuration persist through the existing world and
character-save systems. Real two-client dialogue-plus-recruit acceptance remains
manual.

Mini Mimic Appearance is independent of dialogue and recruitment. `Baby` is the
backward-compatible default and keeps the dedicated shell with its generated
relined mouth surfaces and cavity teeth; `Scaled Mimic` fits the complete regular Mimic slabs into the
Mini footprint. Changing appearance does not clear a dialogue resource, alter
quest scope, or change the `recruit_npc` action. Both modes use the calm idle.

PER-PLAYER QUEST FOUNDATION
---------------------------
Quest state is separate for every multiplayer player slot.
A completed quest is one-time per player: Player A completing Quest A
does not stop Player C from accepting and completing it, but neither
player can accept it again after their own completion.

Runtime key: player_<slot>:<normalized quest ID>
Current persistence: world-companion saves serialize quest/dialogue state, and
dedicated per-character saves export/import the selected player's story state.
The in-memory runtime key remains slot-based; the save/reconnect layer is
responsible for restoring the correct character's state to its current slot.
Party/world quest ownership is still not implemented: authored party/world
values load safely as player scope. Repeatable player quests support the
explicit reset path; complete multiplayer and reconnect regression coverage
remains outstanding.

JSON ROOT
---------
Runtime file: build/dialogue/test.json
Required shape:
{
  "version": 1,
  "quest_id": "torch_for_the_stranger",
  "start_node": 0,
  "nodes": []
}

NODE FIELDS
-----------
id: unique integer node ID
text: NPC text
next: next node; self-reference is terminal
choices: selectable replies
condition: optional redirect
 action: optional one-time consequence

CHOICE FIELDS
-------------
id: stable choice ID
text: displayed reply
next: destination node
once: remember as used
condition: visibility requirement
action: host-authoritative consequences

SUPPORTED CONDITIONS
--------------------
has_item, has_gold, quest_started, quest_accepted, quest_completed,
quest_failed, quest_stage, world_flag, npc_flag, world_variable,
npc_variable, node_seen
Comparisons: equals, not_equals, at_least, at_most
Quest conditions use the interacting player's personal quest state.

SUPPORTED ACTIONS
-----------------
quest_start, quest_accept, quest_stage, quest_complete, quest_fail,
reward_gold, remove_gold, reward_item, remove_item, set_world_flag,
set_npc_flag, set_world_variable, add_world_variable,
set_npc_variable, add_npc_variable, set_quest_variable,
add_quest_variable, objective_complete, objective_clear, quest_reset,
set_power, status_effect, recruit_npc

`recruit_npc` is a boolean action. It does not require an NPC to lose its
authored dialogue configuration, and dialogue plus recruitable is supported.

MULTIPLAYER
-----------
The host validates choices and applies quests, rewards, payments,
variables, flags, and dialogue progression. Remote clients only receive
choices and send a selection.

CURRENT STATUS / ROADMAP
------------------------
Implemented: quest metadata and journal UI, per-player quest/dialogue save
serialization, explicit repeatable-player reset handling, persistent dynamic
items/gold/boulders/monsters for covered entity types, and cross-layer editor
copy/paste paths.

Remaining: true party/world quest ownership, durable platform-level player
identity beyond the saved reconnect/session mechanisms, unsupported dynamic
entity edge cases, and broad graphical/multiplayer save-reload verification.
Shopkeepers later restock after roughly 2-6 distinct map visits, without
repeatedly counting alternation between the same maps.
