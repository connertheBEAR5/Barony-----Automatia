1. EXECUTIVE SUMMARY
====================

The current Automatia tree and the supplied S.A.M. 2.1 source do not represent two
drop-in alternatives. They solve different parts of the same problem and overlap at
several dangerous seams.

Automatia currently contains an intentionally lightweight S.A.M. 1.10 foundation. It
scans mod manifests, builds deterministic class/item catalogs, allocates custom runtime
item slots in [5000, 25000), exports sam_item_catalog.json, installs basic live item
definitions, and threads stable item identifiers through editor templates, persistence,
scores, shops, item actions, and many gameplay packet paths. Its authority rule is:

    stable_id = persistent/cross-session identity
    runtime item id = current-session lookup only

The supplied S.A.M. 2.1 source is a substantially larger runtime framework. It adds or
extends complete class/item registries, Lua 5.4, QuickJS JavaScript/TypeScript, a unified
event wrapper, custom effects/races/sounds/recipes/spells/models/monster overlays,
script HUD and panels, image overlays, world and catalog query APIs, per-save script
state, prefab room injection, mod-defined packets, and registry fingerprint exchange.

A blind replacement is unsafe. Upstream S.A.M. allocates numeric item IDs from load
order and treats those numbers as its engine identity. Automatia already uses the same
numeric range but separately preserves stable IDs across saves, editor content, and
network paths. Running both registries independently would duplicate parsing and risk
different mappings. Replacing Automatia's registry would remove missing-mod record
preservation and the catalog fingerprint currently included in the multiplayer
handshake. Ignoring 2.1 would discard useful mod APIs.

The integration direction is therefore a shared lower-level contract:

    deterministic manifest/content order
                  |
                  +-- Automatia stable identity and persistence authority
                  |
                  +-- S.A.M. 2.1 enriched runtime definitions and mod APIs

S.A.M. spatial APIs require special treatment. The supplied implementation accesses the
single global map and mostly uses legacy map.tiles / default-floor queries. Automatia's
active map global is only a compatibility view of one MapInstance, and Playable-Z keeps
playableFloor, authoredMapLayer and local Entity::z separate. A 2.1 call may operate on
the active instance, but it must never silently affect another MapInstance or default to
floor Z0 when invoked for an upper-floor entity.

The archive contains framework source, schemas, docs and examples, but it does not ship
a patch set for the engine interception sites. The source comments describe many hook
points. Engine integration must consequently be source-driven and cannot be assumed
complete merely because framework files compile.


2. S.A.M. 2.1 ARCHITECTURE
=========================

Version and bundled dependencies
--------------------------------

* sam_logger.hpp identifies the exact framework as 2.1.0.
* Lua 5.4 is vendored as C source under framework/lua54.
* quickjs-ng is vendored as quickjs-amalgam.c plus quickjs.h.
* nlohmann/json single-header 3.11.3 is vendored under framework/nlohmann.
* TypeScript support uses framework/typescript/typescript.js at runtime and a content
  hash cache under the game's output directory.
* Framework source is MIT licensed; the archive does not include Barony source.

Lifecycle
---------

SAMLoader::load() scans already-mounted paths through SAMWorkshop::scan(), clears every
registry/runtime, initializes the script VMs, applies patch/monster overlays, registers
manifest content, loads companion scripts, resolves late references, and publishes a
load summary. SAMLoader::unload() clears scripts, registries, UI, overlays, patches and
temporary resources. S.A.M. expects Barony's Mods::loadMods()/unloadMods() to be the
owner of this lifecycle.

Public API and hooks
--------------------

SAMLua and SAMJs expose parallel host APIs. SamEvent is the 2.1 bridge intended to build
one primitive-only event and dispatch it to both runtimes. Script callbacks receive no
engine pointers. State-changing calls are normally rejected on multiplayer clients.
The event surface supports cancellation and numeric/string write-back at hook sites.

Registries
----------

SAMWorkshop owns dependency-sorted manifests. SAMClasses, SAMItems, SAMEffects,
SAMRaces, SAMSounds, SAMRecipes, SAMSpells, SAMModels, SAMMonsters, SAMImages and
SAMRooms own content-specific registries. Most are process-global and rebuilt per mod
load. This global lifetime is compatible only if each loaded Automatia MapInstance uses
the same mod set and registry mapping.

Resource and overlay systems
----------------------------

SAMPatcher and SAMMonsters create private overlay content for PhysFS. SAMModels grows
the global model table at a controlled load seam. SAMHud and SAMUi retain logical widget
descriptions so they can reconstruct engine Frames destroyed at a floor transition.
SAMImages resolves manifest IDs to local paths and uses host-to-client messages for
remote overlays.

Thread assumptions
------------------

Registry construction, UI access, global map access, script dispatch and engine table
mutation assume the main game thread. Script VM state is global and not synchronized.
The Lua watchdog uses an instruction counter; QuickJS uses a wall-clock interrupt.
Neither makes the host API thread-safe.

Headless assumptions
--------------------

Core scanning, validation, logging, registries and scripting can in principle run
without a renderer. HUD, UI and image modules touch renderer/UI resources and must be
excluded or no-op in a headless process. Sound calls must honor no_sound. Upstream uses
EDITOR compile guards but has no equivalent comprehensive headless guard.


3. EXISTING AUTOMATIA ARCHITECTURE
==================================

Automatia S.A.M. 1.10 foundation
--------------------------------

SAMFoundation is invoked from mod_tools.cpp after Barony mounts mods and is unloaded
before the mounts disappear. It initializes SAMLogger, scans manifests, builds the
foundation class/item registries, rebuilds SAMContentCatalog, installs basic ItemGeneric
definitions through SAMItemDefinitionBridge, runs controlled construction checks, and
exports sam_item_catalog.json.

The game target intentionally compiles only the foundation adapters plus logger,
errors, workshop and sync. The larger 1.10 framework source is present but not linked.
This is an important architecture fact: source presence did not mean gameplay scripting
was active before this upgrade.

Item identity
-------------

items[] has NUM_ITEM_SLOTS storage through 25000 while NUMITEMS remains the vanilla
enumerated count. Automatia reserves [5000, 25000) for S.A.M. definitions and does not
widen vanilla random-generation loops into empty slots. SAMItemRegistryFoundation maps
stable IDs to session runtime IDs. Existing engine patches resolve stable IDs before
accepting transmitted numeric IDs and reject unknown custom slots rather than clamping
them to NUMITEMS - 1.

The editor reads ~/.barony/sam_item_catalog.json into a catalog keyed by both stable ID
and runtime ID. Monster inventory/equipment templates carry stable ID metadata so an
editor-only launch and a later game launch can remap without treating runtime numbers as
persistent identity.

Playable-Z
----------

Entity::z is local animation/model elevation. Entity::playableFloor controls discrete
simulation scope. Entity::authoredMapLayer is the structural layer used to calculate
world render/light Z. SpatialSpawnContext carries playableFloor, spatialRevision and
authoredMapLayer. newEntity() inherits the thread-local active runtime context, while
newEntityWithSpatialContext() explicitly copies a source/context. map_t::tileAt and
setTileAt take playableFloor and understand layer-stack-derived floors.

Divergent paths
---------------

WorldState owns multiple MapInstances. Activating an instance swaps the compatibility
global map/simulation state. A MapInstance key is mapFile#instanceId and is independent
from playableFloor and authoredMapLayer. Network packet scope filters map-local traffic;
late join and persistence carry instance revisions and identities.

Persistence, parties, dialogue and editor
------------------------------------------

Automatia has separate world/character persistence, durable party identities and party
state, divergent-map late join, JSON dialogue/quests, and substantial Zed extensions.
These systems are authoritative existing behavior and cannot be replaced by S.A.M.'s
global per-mod JSON store or its narrower per-character additional_data helper.


4. S.A.M. 1.10 -> S.A.M. 2.1 MIGRATION
======================================

MITIGATED / SOURCE-VERIFIED / MANUAL FIXTURE REQUIRED. Migration inputs are 1.10 manifest/catalog behavior, saved stable IDs,
editor templates and packets. The archive contains no explicit 1.10-to-2.1 catalog
migrator. S.A.M. manifests remain namespace/version based and the 2.1 workshop scanner
is structurally compatible with the current foundation. New manifest fields include
images and rooms; older manifests omit them safely.

Required migration rules:

* Existing stable IDs keep authority even if 2.1 assigns a different session slot.
* Existing sam_item_catalog.json files are input hints for editor/missing-mod content,
  never authority over a live validated registry.
* Missing mods do not cause a saved custom record to be replaced by a vanilla item.
* A restored mod resolves an opaque record by stable ID and leaves its other serialized
  fields intact.
* A 1.10 mod that omits all 2.1 fields loads with the old basic behavior.
* New scripts and registries must not initialize twice during a mount/reload cycle.

6. ITEM REGISTRY / RUNTIME IDS / STABLE IDS
===========================================

DIRECT CONFLICT -- RESOLVED for live registration; persistence gaps are listed below.

Vanilla IDs remain [0, NUMITEMS). Custom storage is arbitrary nonnegative ItemType data
within the current engine storage contract, not a reason to clamp to NUMITEMS - 1.
Automatia currently reserves runtime slots [5000, 25000). The 2.1 SAMItems registry also
starts at 5000 and reserves framework item 6000, so two independent allocators could
write the same slot for different stable IDs.

Integration invariants:

1. stable_id is serialized whenever available.
2. runtime ID is resolved from the live stable registry at use/load/receive time.
3. raw nonnegative unknown runtime IDs may be retained as opaque data but never indexed
   into items[] without a validated bound and live definition.
4. duplicate stable IDs are rejected deterministically with source diagnostics.
5. duplicate requested numeric IDs cannot displace an already registered stable ID.
6. registry exhaustion fails the new declaration, not existing content.
7. signed packet fields and ItemType casts are validated before conversion.
8. missing content remains an unknown custom record, not an unrelated vanilla item.

Affected consumers audited in current source include gameplay inventory actions,
equipment transitions, shops, scores, magic weapons, entity equipment, console item
commands, monster editor templates and many net.cpp receive paths. Additional consumers
that require explicit 2.1 verification are loot candidates, workbench recipes, chest
contents, custom-monster inventory, class/race starting gear, spell payload items,
dialogue/quest checks and Text Source references.

Edge cases:

* Runtime ID 5000 in an old save maps to A; next session it maps to B. Stable A must win.
* A catalog says runtime 70000. Preserve the opaque number but do not index items[].
* Two mods declare the same stable ID. First canonical dependency/namespace order wins;
  second fails visibly. Never let UI order decide.
* A mod is renamed but retains namespace/stable IDs. Content remains compatible; source
  display metadata may change.
* A namespace/stable ID is renamed. Treat as missing old content unless an explicit alias
  migration is declared; do not guess from display name.

8. PLAYABLE-Z
=============

DIRECT CONFLICT for spatial APIs -- MITIGATED; safe adapters implemented, unsupported scopes refused.

Upstream 2.1 SAMWorld::tile/setTile directly index map.tiles and therefore read/write the
legacy compatibility floor. SAMWorld::findEntities walks the active global entity list
without filtering playableFloor. Script spawn APIs call legacy spawn helpers and depend
on ambient runtime context. These are unsafe without adapters.

Every S.A.M.-created spatial object must receive all of:

    active MapInstance (by operating only in the activated map)
    playableFloor
    authoredMapLayer
    local Entity::z
    spatialRevision

Entity creation should use newEntityWithSpatialContext or a scoped
SpatialSpawnContext. A player-targeted operation should derive context from that player's
entity only after confirming the player belongs to the active MapInstance. It must not
activate a different instance re-entrantly from inside an entity behavior.

Specific audits:

* Items/monsters/projectiles/particles: inherit caller/owner context before creation.
* Child entities: use source inheritance; do not translate bodyparts twice.
* Lights: pass playableFloor and structural authored layer to floor-aware addLight.
* Tiles/pathing: use map.tileAt/setTileAt and floor-specific path maps.
* Effects: non-spatial data may attach to an entity; packets still need entity scope.
* Legacy one-floor maps: default context remains floor 0/layer 0/revision 0.
* Same X/Y on floors 0 and 5: queries and collisions return only the requested floor.


9. DIVERGENT PATHS / MAPINSTANCE
================================

DIRECT CONFLICT for global world calls -- MITIGATED by an active-instance-only contract.

S.A.M. process-global registries are acceptable only if every MapInstance in one process
uses the same mounted mod set. Spatial state is not process-global. Scripts may inspect or
mutate only the currently activated instance unless an explicit validated instance API is
added later. MapInstance is never inferred from playableFloor.

Room generation must use the same canonical injected room list and seed for every peer
and every generation of a given content set. Unload/reload must not leave pointers to
overlay files. Late join must receive the same registry fingerprint before accepting
custom state.


10. PERSISTENCE
===============

MAJOR OVERLAP -- MITIGATED for items/world records; S.A.M script world-state bridge is DEFERRED.

S.A.M. 2.1 SAMWorldState stores namespaced strings in SaveGameInfo.additional_data and
caps key/value/total sizes. Automatia has broader character and world persistence,
including multiple MapInstances and true-Z context. SAMWorldState may be a compatibility
front end, but Automatia's save transaction remains authority.

Unknown custom item/entity/monster/mechanism records must retain their stable content ID,
source metadata and opaque extension state. Corrupt extension records fail locally and do
not invalidate unrelated vanilla/world records. A headless restart must rebuild the same
registry before resolving state.


11. HEADLESS SERVER
===================

MAJOR OVERLAP -- MITIGATED and BUILD TESTED; live dedicated-server acceptance remains MANUAL.

Core registries, scripts and gameplay hooks must not require gui, renderer, Image, SDL
window, local player, audio device, editor or Steam client. HUD/UI/image calls on headless
must return a documented false/no-op. no_sound must prevent sound API work. Manifest
discovery uses already-mounted paths and therefore does not require Steam.


12. 15-PLAYER MULTIPLAYER
=========================

MAJOR OVERLAP -- MITIGATED and compile-characterized for MAXPLAYERS=15; live session is MANUAL.

Most supplied loops use MAXPLAYERS, which will expand correctly. Several comments and API

All custom packets must validate player index, length, sender authority and active map

=====================

14. ZED EDITOR
==============

MAJOR OVERLAP -- MITIGATED; existing editor capability is preserved, rich new entity UI is DEFERRED.

Keep Automatia's catalog-backed item selection, stable-ID monster inventory/equipment

15. ROOM GROUPS / ROOM GENERATION
=================================

MAJOR OVERLAP -- RESOLVED at the generation-provider seam; live deterministic MP remains MANUAL.

S.A.M. 2.1 SAMRooms reads manifest entries shaped as levelset -> list of prefab .lmp
paths. It canonicalizes ordering by namespace/relative path because generateDungeon uses
the room list as an RNG index space and clients regenerate from a shared seed.

Automatia has two distinct room-related capabilities that must remain:

* Zed cuboid/multi-layer room selection and whole-room clipboard operations.
* Existing generateDungeon room/subroom pools and special/treasure/shop placement logic.

Best-of-both-worlds design:

    canonical generation room provider
             |
             +-- vanilla/Automatia levelset room sequence and subroom rules
             |
             +-- sorted S.A.M. injected prefab descriptors

The provider must append S.A.M. rooms without changing the no-mod list or RNG consumption.
Automatia editor selection metadata is not replaced by SAMRooms. A future shared room
descriptor may expose cuboid bounds/editor metadata, but 2.1's file-path injection does
not contain enough information to become the editor's room representation.

Required tests: no-mod seed equivalence; one injected room; multiple mods in opposite UI
orders; dependency ordering; missing room file; duplicate path; 32-layer room; room with
stairs/Playable-Z metadata; divergent generated instances; host/client regeneration;
late join; removed mod on reload; old map with no extension metadata.

23. NETWORKING PROTOCOL
=======================

MAJOR OVERLAP -- DEFERRED at the mandated protocol-redesign stop boundary.

S.A.M. defines SAMF (fingerprint), SAMP (mod envelope), SAMA (action edge), SAMS (speed),
SAMI (image), SAMT (tile), and other feature messages in the runtimes. Automatia already
extends item packets with stable IDs and scopes simulation packets to MapInstance.

No casual redesign is permitted. Each additive packet needs a length/version check,
sender direction check, slot bound, payload cap, map-scope decision, and late-join gate.
If correct registry synchronization requires redesigning existing packets rather than an
additive handshake, implementation stops before that redesign.


24. REGISTRY HANDSHAKE / MOD MISMATCH
=====================================

DIRECT CONFLICT -- MITIGATED in fingerprint data; live pre-game enforcement is DEFERRED.

Upstream SAMSync compares namespace@version only. Automatia's current SAMSync deliberately
adds __sam_content_catalog__@<fingerprint>. Preserve that addition. Namespace/version
equality is insufficient when files differ or a registration failed. A mismatch warns and
must prevent unsafe custom-ID interpretation; whether to hard-block gameplay is a product
decision and is not silently changed here.


25. MOD LOAD ORDER
==================

MAJOR OVERLAP -- RESOLVED for deterministic registries/rooms; live dependency permutations are MANUAL.

Use dependency-safe canonical order with namespace ordering for independent mods. UI click
order and PhysFS enumeration order cannot assign runtime identity or room RNG indices.
Duplicate namespaces, dependency cycles and missing required dependencies fail
deterministically. Optional dependencies may affect hooks only through documented order.


26. RESOURCE LIFETIME
=====================

MAJOR OVERLAP -- MITIGATED; unload order is implemented and source-reviewed.

Unload order must stop callbacks/timers before freeing registries/models/images/overlay
files. Entity behavior tags must be cleared or retained as inert placeholders before VM
functions are released. UI retained descriptions cannot refer to unloaded image paths.
Save serialization cannot hold raw registry pointers.


27. ERROR HANDLING
==================

MINOR OVERLAP -- MITIGATED; validation/logging present, malformed-content fuzzing is DEFERRED.

Malformed JSON, invalid stable IDs, missing files, duplicate declarations, capacity
exhaustion and script errors are isolated per record/script. Logs include mod namespace,
source path and field. A recoverable mod error does not crash the host or invalidate
unrelated content. Do not catch and hide engine invariant failures.


28. PERFORMANCE
===============

MINOR OVERLAP -- MITIGATED; load-time registries/caches retained, profiling is MANUAL.

Registries build at mod load, not per frame. SamEvent is intended to avoid building two
events when no scripts listen. Entity/world scans require radius and result caps plus
playableFloor filtering. Room lists are pre-sorted. UI is retained. Script memory and
instruction/time budgets stay enabled. Avoid re-generating path maps per tile edit; batch
or defer once per affected floor.


29. COMPILE-TIME / HEADER DEPENDENCY IMPACT
===========================================

MAJOR OVERLAP -- RESOLVED for public-header fanout; clean-build RAM measurement is DEFERRED.

nlohmann/json.hpp is 24,765 lines and must remain implementation-local. Public Automatia
headers already need review where they include it. S.A.M headers mostly use std types and
forward declarations, but sam_event.hpp directly includes both complete runtime headers.
Prefer a lightweight event declaration/pimpl or implementation-local runtime includes
before exposing SamEvent widely. Build the runtime in a dedicated target/object group so
QuickJS/Lua/json parsing does not fan out across ordinary Barony translation units.


30. THREADING / ASYNC
=====================

MAJOR OVERLAP -- MITIGATED: engine resource append occurs after async joins on the main thread.

All engine-facing S.A.M calls are main-thread only. Do not dispatch scripts from async map
generation or assignActions workers while process-global map/registries are being swapped.
Room registry reads can be immutable during generation, but applying/reloading rooms is a
barrier operation. No callback may outlive mod unload.


31. SECURITY / TRUST BOUNDARIES
===============================

MAJOR OVERLAP -- MITIGATED by host authority/sandboxes; packet and fuzz work is DEFERRED.

Mod JSON/scripts and all client packets are untrusted. Preserve Lua/QuickJS sandbox caps,
no filesystem/network/OS libraries, primitive-only events and per-script disable-on-error.
Validate paths against traversal and keep writes under controlled output directories.

C. S.A.M. 1.10 TO 2.1 MIGRATION
--------------------------------

Status: MITIGATED / SOURCE-VERIFIED / MANUAL MOD TEST REQUIRED.

Automatia's previous 1.10-era manifest scan, stable registry, catalog exporter, class
selection integration and stable item persistence were preserved. S.A.M. 2.1 manifests
are a compatible superset: omitted 2.1 arrays and fields default to empty, so a basic
1.10 manifest is accepted without rewriting it. The migration does not rewrite old maps,
saves, templates or sam_item_catalog.json.

The stable-id allocator runs before the rich 2.1 item loader. Therefore a 1.10 item keeps
the Automatia session mapping chosen for its stable ID, while any richer 2.1 definition
stamps traits, tooltips, model metadata and attributes into that same slot. The fixed
2.1 Hunter's Workbench is reserved as stable ID sam:hunters_workbench at runtime 6000
before mod allocation. Mod allocation scans the complete [5000,25000) range and skips
occupied 6000; it does not sacrifice the old 20,000-slot capacity contract.

No alias mechanism was invented for renamed namespaces/stable IDs. A renamed ID remains
missing until a mod supplies an explicit future migration; guessing by display name could
silently convert an old object into unrelated content.


D. ITEM IDENTITY, CATALOG, AND CONSUMERS
----------------------------------------

Status: RESOLVED for registry/session mapping; MITIGATED for every possible consumer.

One lightweight header now owns these constants without importing JSON or runtime code:

    vanilla IDs            [0, NUMITEMS)
    custom runtime slots   [5000, 25000)
    capacity               20,000
    fixed 2.1 workbench    6000

The Automatia foundation remains the only integrated allocator. SAMItems accepts a
stable-id resolver callback and refuses a rich definition with no valid mapping. Its
standalone fallback also uses the full range and skips 6000. Registry exhaustion returns
failure; it does not clamp, wrap or displace an existing definition. Duplicate stable IDs
remain deterministically rejected by the foundation. Custom trait declarations are
folded into a uint64 mask stored in ItemGeneric; unload/data reload clears/reapplies the
mask so a removed mod cannot leak behavior into a later runtime occupant.

Connected item behavior includes:

* rich definitions and tooltip restoration after vanilla data readers clear tables;
* custom model append/late resolution;
* random loot candidate participation by category and level;
* weapon proficiency override;
* ranged, quiver, foci, instrument, thrown-ball, potion-bad and beatitude-AC traits;
* persistent world items and persistent monster inventory/equipment acceptance;
* floor-summary inspection without replacing a registered custom item by GEM_ROCK;
* existing Automatia stable-ID packet/save/editor/shop/score/magic paths remain intact.

Unknown nonnegative item IDs may be retained by existing opaque persistence fields, but
are never safe for items[] indexing without [0,NUM_ITEM_SLOTS) plus live-registration
validation. The integration introduces no NUMITEMS-1 clamp for custom content. Existing
vanilla clamps in unrelated legacy monster code are not treated as S.A.M registration
paths and were not broadly rewritten in this task.

sam_item_catalog.json keeps Automatia's versioned schema, range metadata, fingerprint,
stable/runtime mapping and atomic publication. The workbench participates in the same
catalog when S.A.M mods are active. Catalog runtime numbers are informational for the
specific fingerprint/session; stable_id remains authority. Editor and missing-mod views
may display an old catalog, but gameplay never accepts that file as a substitute live
registry.

Residual item cases requiring content fixtures/manual sessions: shop-specific exclusion
attributes on custom loot, all crafting recipe combinations, real chest UI, custom class
starting equipment, restored-mod visual reconstruction, and a live item with runtime ID
above 32767 crossing every relevant packet family.


E. PLAYABLE-Z AND DIVERGENT MAPS
--------------------------------

Status: MITIGATED / CHARACTERIZATION TESTED.

The narrow Automatia scripting adapter creates a ground item through newEntity while a
SpatialSpawnContext is active. This inherits playableFloor, authoredMapLayer and
spatialRevision. It assigns Entity::z = 0 as local model elevation and never derives a
layer from z. Tile validation uses map.tileAt(..., activeRuntimePlayableFloor()).

SAMWorld tile reads use map.tileAt on the active playable floor. Entity lookup/find
filters by activeRuntimePlayableFloor, preventing same-X/Y entities on other floors from
matching. Terrain writes use map.setTileAt for single-player. Path connectivity refuses
nonzero floors because the current global path-map API cannot name a playable floor;
returning false is safer than answering with floor-zero geometry.

S.A.M calls operate only on the currently activated MapInstance. There is deliberately
no API that takes an arbitrary instance key and re-enters WorldState from inside a script
callback. Thus MapInstance and playableFloor remain orthogonal, but scripts cannot mutate
a dormant divergent instance. That restriction is a KNOWN LIMITATION, not a collapse of
the two axes.

The Stage 4D/Z3.4C characterization executable passed after integration. It genuinely
characterized legacy local-z safety, ELYR authored-layer round trip, structural render/
light context, multipart spawn floors, falling/landing, persistent ownership, minimap
floor isolation, and stacked stairs. It did not execute a graphical S.A.M projectile,
particle, light or custom-monster body; those remain MANUAL TEST REQUIRED. Upstream 2.1
spawn APIs other than the adapted ground-item seam must be reviewed as each engine hook
is connected; merely inheriting ambient context is not accepted as proof.


F. ROOM GROUPS AND PROCEDURAL GENERATION
----------------------------------------

Status: RESOLVED architecture / SOURCE-CONTRACT TESTED / LIVE MP MANUAL.

Automatia's Zed cuboid/multi-layer selection, whole-room clipboard, Room Groups, vanilla
subrooms, shop/treasure/special placement and existing generation algorithms remain.
SAMRooms is an additive provider only:

    existing canonical mapList (entrance remains index 0)
              + sorted valid S.A.M prefab paths for this levelset

An injected room is passed through the current loadSubRoomData parser, so it receives the
same LMP/Playable-Z validation as any other room. Unreadable paths are rejected before
numlevels increases. With no registered rooms the loop is a no-op and consumes no RNG.
SAMRooms clears on unload, preventing stale absolute paths and preventing no-mod seed/RNG
range drift after a mod is removed.

This is the best-of-both-worlds reconciliation: a shared generation input seam, not a
replacement editor model and not two competing dungeon generators. A future richer
shared room descriptor may expose cuboid/editor metadata, but S.A.M. 2.1 supplies only
levelset/path injection and cannot truthfully represent Automatia Room Group geometry.

Live host/client regeneration with actual injected 32-layer rooms is not automated.
Because safe registry negotiation is not live-wired, S.A.M rooms must not be used in a
multiplayer lobby until host and clients have been manually confirmed to use identical
content. Hard gating belongs to the deferred protocol work below.


G. PERSISTENCE
--------------

Status: MITIGATED; core custom item records preserved; S.A.M extension-state bridge DEFERRED.

Existing Automatia character/world persistence remains authority for containers, dropped
items, monster inventories/equipment, companions, MapInstances and Playable-Z context.
Capture paths that previously accepted only < NUMITEMS now also accept a live registered
custom ID and retain the existing stable ID. Loading resolves stable ID against the live

H. MULTIPLAYER PROTOCOL STOP REPORT
-----------------------------------

Status: DEFERRED by explicit task boundary; existing Automatia packets were not redesigned.

The supplied 2.1 runtime defines SAMF, SAMP, SAMA, SAMS, SAMI and SAMT messages. The
archive contains send/receive helpers and comments describing engine handler seams, but
the current Automatia net dispatcher has no live handler calls for this family. More
importantly, spatial messages do not carry MapInstance, playableFloor, authoredMapLayer
or spatialRevision. Namespace@version comparison alone is insufficient; Automatia's
content fingerprint extension is retained in SAMSync but not yet invoked as a mandatory
pre-game handshake.

This is a significant protocol design, not a safe incidental packet patch. The required
future protocol must include at least:

1. a negotiated protocol/version/capability frame before accepting S.A.M content;
2. full content-catalog fingerprint and deterministic registration result, not only mod
   namespace/version;
3. a hard safe failure or content-disable decision before procedural generation;
4. sender direction and server-authority validation per message;
5. MAXPLAYERS-sized player validation for slots 0..14;
6. explicit MapInstance identity plus playableFloor and spatialRevision for every spatial
   mutation/effect, and authoredMapLayer wherever structural placement needs it;
7. bounded payload/tag/image/state sizes and integer-width validation;
8. late-join snapshot/order rules, disconnect/reconnect ownership, duplicate/replay rules;
9. behavior for vanilla peers and peers with framework but different capability sets;
10. fuzz tests plus host/client/dedicated-server divergent-map acceptance.

Until that design exists, multiplayer sam_set_tile refuses all writes. Script ticks stay
host-authoritative, and no new incoming S.A.M packet handler was added. Other upstream
packet-emitting script APIs are linked but have no Automatia receive integration; mods
must treat them as unavailable in Automatia multiplayer. This limitation is explicit so
unknown packets cannot be mistaken for tested synchronization.

The MAXPLAYERS == 4 static assertion in upstream move-speed state was removed. Storage is
now std::array<double, MAXPLAYERS> initialized to 1.0, and the full game compiles with the
Automatia 15-player configuration. This proves the corrected allocation/compile contract,
not a live fifteen-client run.

   editor geometry remain intact.

   ambiguous operations; local Entity::z never becomes a layer.

8. Existing packets were not casually changed. The missing scope/handshake problem is
   isolated as an explicit protocol project.
9. Features whose framework code is linked but whose engine interception/persistence is
   incomplete are documented as incomplete; presence is not reported as behavior.
10. Legacy content and no-mod behavior stay additive/no-op by construction.
