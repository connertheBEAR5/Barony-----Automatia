BARONY AUTOMATIA HEADLESS SERVER DEVELOPER GUIDE
================================================

IMPLEMENTED LAUNCH MODES

Safe idle mode:
  ./barony --headless

This suppresses the visible window, sound, and controller initialization. It does not open a network listener.

LAN lobby:
  ./barony --headless --LAN --port=57165 --server-name=AutomatiaLAN

This opens the existing Barony direct-connect UDP lobby on 0.0.0.0:<port>. Clients may join before the game begins.

Autostart immediately:
  ./barony --headless --LAN --autostart

Autostart after a delay:
  ./barony --headless --LAN --autostart=30

The delay is in seconds. Without --autostart, the server remains in the pre-game lobby.

SECURITY BEHAVIOR

Plain --headless fails closed and opens no socket.
--LAN explicitly opens the direct-connect UDP listener.
--public is rejected because public listing and platform authentication are not yet implemented safely.
--private requires a password, and password hosting is rejected until challenge-response authentication exists.
The plaintext password is never written to logs or the status file.
--late-join records intent, but joining a game already in progress is not implemented. Joining the pre-game lobby works.

STATUS

Terminal output clearly prints whether a listener opened and the actual UDP port.
A status file is written to ~/.barony/headless_server_status.txt.

CURRENT ARCHITECTURAL LIMITATIONS

The process still creates a hidden OpenGL context because game resource initialization is not fully separated from rendering.
There is no stdin administrative console yet.
There is no public lobby registration, password challenge-response, in-progress late join, or crash-safe dedicated save restart yet.
These are not represented as complete or secure.

DEVELOPER REQUIREMENTS

Never expose a port unless an explicit hosting argument was supplied.
Never claim password protection unless the server validates a challenge before accepting JOIN.
Never log plaintext passwords.
Late join must synchronize map identity, entities, players, mechanisms, quests, followers, containers, shops, and S.A.M. stable IDs before enabling player control.
All custom items must use stable_id as authoritative identity. Runtime item IDs are session-local mappings.

HEADLESS-2 ADMINISTRATION AND RELIABILITY
=========================================
The combined follow-up package adds a POSIX terminal administration console.
Commands are entered in the same terminal that launched the server:

  help
  status
  start
  shutdown

"start" begins the game from the waiting LAN lobby. "shutdown" exits through
the normal main-loop cleanup path. The server never accepts --late-join,
--public, or password hosting as if those features were complete.

FAIL-CLOSED FEATURE BOUNDARIES
==============================
The following options remain intentionally unavailable:

* Public listing: requires Steam/EOS/platform lobby registration and identity.
* Password protection: requires a nonce-based authenticated handshake and rate
  limiting. A plaintext command-line password must never be sent in an ordinary
  gameplay packet.
* In-progress late join: requires a versioned full-state snapshot containing
  maps, entities, players, mechanisms, quests, followers, shops, containers,
  and S.A.M. stable IDs.
* True renderless operation: simulation data loading is still coupled to an
  OpenGL-backed resource startup path. The current server uses a hidden context.
* Automatic save/restart recovery: belongs to the final disk-backed world-save
  project so it can use authoritative stable IDs and versioned migrations.

A developer must not remove these rejections until the underlying mechanism is
implemented and tested. Logging an option is not equivalent to enforcing it.

CROSS-PLATFORM CONSOLE SUPPORT
==============================

The headless administrator console supports both Linux/POSIX and Windows builds.

Linux/POSIX uses select() on standard input so the game loop is never blocked waiting for a command.

Windows uses _kbhit() and _getch() from conio.h. Input is accumulated without blocking the simulation. Enter submits a command, Backspace edits the current command, and extended keyboard codes are ignored safely.

The shared command dispatcher implements:

  help
  status
  start
  shutdown

Windows launch example:

  barony.exe --headless --LAN --port=57165 --server-name=AutomatiaLAN

Windows Firewall notes:

- The first listener startup may trigger a Microsoft Defender Firewall prompt.
- For a LAN-only server, permit the executable on Private networks only.
- Do not instruct users to disable Windows Firewall.
- UDP port forwarding is not needed for machines on the same LAN.
- Internet hosting requires router/firewall configuration and is outside the security guarantees of the current LAN-only implementation.

Build portability requirements:

- Keep Windows-only headers inside WINDOWS preprocessor guards.
- Keep POSIX-only headers and APIs outside Windows builds.
- Do not introduce pthread-only, fork(), daemon(), or Unix-domain-socket assumptions into the shared server loop.
- Use SDL and SDL_net abstractions for networking and timing where practical.
- Test MinGW and Visual Studio builds separately because their runtime and console behavior can differ.
