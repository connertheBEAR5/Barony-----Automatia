BARONY AUTOMATIA HEADLESS SERVER DEVELOPER GUIDE
================================================

IMPLEMENTED LAUNCH MODES

Safe idle mode:
  ./barony --headless

This suppresses the visible window, sound, and controller initialization. It does not open a network listener.

LAN lobby:
  ./barony --headless --LAN --port=57165 --server-name=AutomatiaLAN

This opens the existing Barony direct-connect UDP lobby on 0.0.0.0:<port>. Clients may join before the game begins.

Autostart immediately:
  ./barony --headless --LAN --autostart

Autostart after a delay:
  ./barony --headless --LAN --autostart=30

The delay is in seconds. Without --autostart, the server remains in the pre-game lobby.

Persistent save slot with a five-minute autosave:
  ./barony --headless --LAN --autostart --save=0 --autosave=300

Autosave is disabled by default. This build accepts numeric slots 0 through 99;
arbitrary path targets are rejected rather than interpreted as a slot. At
startup, an empty configured slot begins a new session. A valid LAN-server save
is restored before autostart or an administrator `start`; a malformed,
incompatible, or unreadable existing slot closes the listener and stops startup
so the file cannot be overwritten accidentally.

SECURITY BEHAVIOR

Plain --headless fails closed and opens no socket.
--LAN explicitly opens the direct-connect UDP listener.
--public is rejected because public listing and platform authentication are not yet implemented safely.
--private requires a password, and password hosting is rejected until challenge-response authentication exists.
The plaintext password is never written to logs or the status file.
--late-join explicitly enables the experimental direct-connect LAN runtime JOIN
path. The versioned snapshot handshake, S.A.M. catalog fingerprint check, and
pre-authorization simulation gate are implemented. Bounded incremental catch-up,
explicit abort/timeout cleanup, and per-slot reconnect bearer tokens are also
present. Contained new-player UDP probes pass; normal graphical two-client and
token-matched returning-player acceptance remain. The option does not enable public,
password-protected, Steam, or EOS late joining.

STATUS

Terminal output clearly prints whether a listener opened and the actual UDP port.
A status file is written to ~/.barony/headless_server_status.txt.

CURRENT ARCHITECTURAL LIMITATIONS

The process still creates a hidden OpenGL context because game resource initialization is not fully separated from rendering.
There is no public lobby registration or password challenge-response. Direct-LAN
in-progress late join still needs a two-client acceptance run. Dedicated slot
save and recovery have passed a Linux start/save/restart/resave runtime test,
but still need divergent-player and Windows verification. Reconnect now has a
per-slot 128-bit bearer identity stored in compatible saves; the corrected
token-matched returning-player branch still needs a current live acceptance run,
and the token is not a durable platform account identity.
These are not represented as complete or secure.

DEVELOPER REQUIREMENTS

Never expose a port unless an explicit hosting argument was supplied.
Never claim password protection unless the server validates a challenge before accepting JOIN.
Never log plaintext passwords.
Late join must synchronize map identity, entities, players, mechanisms, quests, followers, containers, shops, and S.A.M. stable IDs before enabling player control.
All custom items must use stable_id as authoritative identity. Runtime item IDs are session-local mappings.

HEADLESS-2 ADMINISTRATION AND RELIABILITY
=========================================
The combined follow-up package adds a POSIX terminal administration console.
Commands are entered in the same terminal that launched the server:

  help
  status
  start
  save
  shutdown

"start" begins the game from the waiting LAN lobby. "save" writes the normal
character save and atomic Automatia world companion for the configured slot.
"shutdown" attempts the same save for an active savable server game, reports
failure if one occurs, and then exits through the normal cleanup path. The
server accepts --late-join only for the explicit direct-LAN experimental path;
it never accepts --public or password hosting as if those features were complete.

FAIL-CLOSED FEATURE BOUNDARIES
==============================
The following options remain intentionally unavailable or limited:

* Public listing: requires Steam/EOS/platform lobby registration and identity.
* Password protection: requires a nonce-based authenticated handshake and rate
  limiting. A plaintext command-line password must never be sent in an ordinary
  gameplay packet.
* In-progress late join is limited to explicit direct-connect LAN hosting. Its
  versioned map-instance snapshot, bounded reliable chunks, S.A.M. fingerprint,
  ready/authorize/go handshake, live-output gate, bounded catch-up, abort/timeouts,
  and reconnect bearer tokens are implemented. Live two-client and returning-
  player acceptance, adversarial transport stress, and Steam/EOS transport
  remain required.
* True renderless operation: simulation data loading is still coupled to an
  OpenGL-backed resource startup path. The current server uses a hidden context.
* Restart recovery is limited to an explicitly selected numeric LAN-server save
  slot. Linux start/save/restart/resave acceptance passes for a single occupied
  map. Divergent-player and Windows acceptance remain, and recovery supplies only
  compatible session-slot placement plus its saved bearer token, not a platform
  account identity.

LINUX RUNTIME ACCEPTANCE
========================
On 2026-07-31, the FMOD build passed an isolated direct-LAN runtime cycle:

1. Open a UDP listener with --LAN --late-join and autostart.
2. Load start.lmp#world and enter live gameplay.
3. Execute the administrator shutdown command.
4. Write the normal server save and schema-v3 Automatia companion atomically,
   with the same transaction ID under savegames/host/.
5. Restart from the same numeric slot.
6. Validate the slot, restore the Automatia map record and mechanism state, and
   enter live gameplay again.
7. Execute a second clean save and shutdown.

This test also found and fixed a headless/FMOD title-fade null dereference: sound
suppression left the intro-music array uninitialized while a compiled SOUND path
could still index it. Menu music transitions now validate no_sound, the array,
the track bounds, and the selected sound pointer before use.

A developer must not remove these rejections until the underlying mechanism is
implemented and tested. Logging an option is not equivalent to enforcing it.

CROSS-PLATFORM CONSOLE SUPPORT
==============================

The headless administrator console supports both Linux/POSIX and Windows builds.

Linux/POSIX uses select() on standard input so the game loop is never blocked waiting for a command.

Windows uses _kbhit() and _getch() from conio.h. Input is accumulated without blocking the simulation. Enter submits a command, Backspace edits the current command, and extended keyboard codes are ignored safely.

SIGINT is converted into a main-loop graceful shutdown request. POSIX builds
also handle SIGTERM this way; all file I/O occurs in the normal game loop, not
inside the signal handler.

The shared command dispatcher implements:

  help
  status
  start
  save
  shutdown

Windows launch example:

  barony.exe --headless --LAN --port=57165 --server-name=AutomatiaLAN

Windows Firewall notes:

- The first listener startup may trigger a Microsoft Defender Firewall prompt.
- For a LAN-only server, permit the executable on Private networks only.
- Do not instruct users to disable Windows Firewall.
- UDP port forwarding is not needed for machines on the same LAN.
- Internet hosting requires router/firewall configuration and is outside the security guarantees of the current LAN-only implementation.

Build portability requirements:

- Keep Windows-only headers inside WINDOWS preprocessor guards.
- Keep POSIX-only headers and APIs outside Windows builds.
- Do not introduce pthread-only, fork(), daemon(), or Unix-domain-socket assumptions into the shared server loop.
- Use SDL and SDL_net abstractions for networking and timing where practical.
- Test MinGW and Visual Studio builds separately because their runtime and console behavior can differ.

CURRENT SPATIAL SAVE CONTRACT
=============================

The dedicated server is authoritative for both divergent MapInstances and the
playable-Z stack inside each instance. Persistent player and dynamic-entity
records keep these values distinct:

  map_file + instance_id   which world instance owns the record
  playable_floor          gameplay/spatial slice
  authored_map_layer      physical structural layer, 0..31
  position z              local entity/model Z

Tile overrides additionally include playable floor, X, Y, and geometry layer,
so identical coordinates on two floors remain independent. The companion
validator rejects unknown schema-v3 floors, invalid structural layers,
non-finite local positions, and duplicate tile keys. Older records without an
authored layer use only explicit derived-stack migration semantics.

A headless server does not treat process slot 0 as a player. Per-character save
modes keep disconnected remote character state in the character file; normal
world-companion records and divergent return histories retain their exact map
instance and playable-Z coordinates.

CURRENT VALIDATION SNAPSHOT (2026-08-23)
========================================

The maintained Linux build is the Steamworks-enabled 15-player
build-super-posix profile. Build it with:

  cmake --build build-super-posix -j6

The most recent source-validation run passed that build, all 6 configured CTest
tests, and the Stage 4D/Z3 executable characterization. The contained direct-LAN
new-player late-join probes and the single-occupied-map Linux
start/save/restart/resave cycle also pass.

Those results do not replace the remaining live acceptance work: a normal
graphical two-client late join, token-matched returning-player reconnect,
divergent multi-map/floor save and restart, Windows recovery, Steam/EOS
transport, and adversarial loss/reordering stress are not yet runtime verified.

Playable-Z rendering and persistence remain deliberately separate. A headless
save records MapInstance, playableFloor, authoredMapLayer, and local entity Z;
the legacy one-floor visualLightmapLayer() compatibility rule for ceiling
models is renderer-only and does not reinterpret saved spatial state.

STEAM/OFFLINE BOUNDARY
======================

--nosteam is a local runtime mode that skips SteamAPI initialization. It does
not verify Steam base-game ownership, and Steam DLC remains unavailable. It
does not read or reproduce Steam's offline cache. For an offline session that
must retain owned DLC, start the real Steam client in Offline Mode and launch
without --nosteam so Steamworks remains the entitlement authority.
